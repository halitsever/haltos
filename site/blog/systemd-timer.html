Scheduling a daily job with a systemd timer instead of cron

A systemd timer is a unit that starts another unit on a schedule. It does what a cron line does, with logs in the journal, a status you can query and options for random delays and missed runs. This post explains the pieces using the timer HaltOS installs to check for new releases once a day, read from a running HaltOS 1.2 server.

Two units

A timer never runs a command itself. It starts a service with the same name. HaltOS writes both in install_update_check (install.sh).

/etc/systemd/system/haltos-update-check.service:

[Unit]
Description=Check for a newer HaltOS release
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
ExecStart=/opt/haltos/install.sh check-update

/etc/systemd/system/haltos-update-check.timer, as systemctl cat printed it on a HaltOS 1.2 server:

[Unit]
Description=Check for a newer HaltOS release every day

[Timer]
OnBootSec=5min
OnUnitActiveSec=1d
RandomizedDelaySec=1h
Persistent=true

[Install]
WantedBy=timers.target

Type=oneshot means the service runs to completion and stops. The check writes the newest release tag to /var/lib/haltos/latest, and the SSH login banner reads that file, so logging in never waits for the network.

Enable the timer, not the service:

sudo systemctl daemon-reload
sudo systemctl enable --now haltos-update-check.timer

Monotonic and calendar timers

The systemd.timer manual has two kinds of trigger.

Monotonic, relative to an event: OnBootSec= counts from boot, OnUnitActiveSec= from the last time the service was started, and OnActiveSec=, OnStartupSec= and OnUnitInactiveSec= from other points. The HaltOS timer fires five minutes after boot, then a day after each run.

Calendar, wall-clock times with OnCalendar=:

$ systemd-analyze calendar daily "Mon..Fri 09:00"
  Original form: daily
Normalized form: *-*-* 00:00:00
    Next elapse: Sun 2026-11-29 00:00:00 UTC

  Original form: Mon..Fri 09:00
Normalized form: Mon..Fri *-*-* 09:00:00
    Next elapse: Mon 2026-11-30 09:00:00 UTC

systemd-analyze calendar is the quickest way to check an expression before you put it in a unit.

RandomizedDelaySec

The manual describes it as a random delay between 0 and the given time, evenly distributed. With 1h, a thousand servers that booted at the same moment do not all ask GitHub for the latest release in the same second. On the HaltOS server the next run was listed at 03:18:42, not at a round hour.

Persistent, and a detail in this timer

Persistent=true stores the time of the last run on disk and, after downtime, starts the service right away if a run was missed. The manual is specific: it only has an effect on timers configured with OnCalendar=. The HaltOS timer uses only OnBootSec and OnUnitActiveSec, so its Persistent=true does nothing. In practice OnBootSec=5min already covers a machine that was off, since the check runs shortly after every boot. If you copy this timer with an OnCalendar= line instead, Persistent= starts to matter.

Checking on a timer

$ systemctl list-timers haltos-update-check.timer --all
NEXT                        LEFT LAST                        PASSED UNIT                      ACTIVATES
Sun 2026-11-29 03:18:42 UTC  16h Sat 2026-11-28 03:01:34 UTC 8h ago haltos-update-check.timer haltos-update-check.service

Output of the service goes to the journal:

journalctl -u haltos-update-check.service --since today

Run the job by hand by starting the service: sudo systemctl start haltos-update-check.service.

For a one-line personal job, cron is fine. For something you ship to other machines, like HaltOS's update check, a timer gives you status and logs without extra code. The update itself never runs from the timer: the self-updating scripts post explains why HaltOS only reports new releases and waits for sudo haltos update.

User timers work the same way under ~/.config/systemd/user/ with systemctl --user.

Questions

What is the difference between a systemd timer and cron?

A cron line runs a command. A systemd timer starts a service unit, so the job gets the journal, systemctl status, dependencies, resource limits and an exact record of the last and next run. Cron is shorter to write.

Does Persistent=true work with OnBootSec?

No. The systemd.timer manual says Persistent= only has an effect on timers configured with OnCalendar=. Timers built from OnBootSec and OnUnitActiveSec ignore it.

How do I see when a systemd timer runs next?

systemctl list-timers shows the next and last run of every active timer. systemd-analyze calendar shows when an OnCalendar expression would fire.
